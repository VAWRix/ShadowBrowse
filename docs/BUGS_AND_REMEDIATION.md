## 2. Fixed Defects

### Bug SB-FIX-001: DeclarativeNetRequest Referrer Rule Error on Extension Boot

- **Severity:** HIGH / RUNTIME BREAKAGE
- **Affected File:** `extension/src/background/trackerDefenseController.ts`
- **Reproduction Steps:**
  1. Boot extension or call `TrackerDefenseController.getInstance().setReferrerMode('STANDARD')`.
  2. Observe runtime execution of `syncReferrerHeaderRule()`.
  3. Chromium's `declarativeNetRequest.updateDynamicRules` rejects with error: `"Rule with id 9001 is invalid: value is required for 'set' and 'append' operations."`
- **Root Cause:**
  In lines 403-404 of `trackerDefenseController.ts`:
  ```ts
  operation: (this.referrerMode === 'STRICT' ? 'remove' : 'set') as chrome.declarativeNetRequest.HeaderOperation,
  value: this.referrerMode === 'STANDARD' ? undefined : undefined,
  ```
  In `STANDARD` mode, `operation` was evaluated as `'set'`, while `value` was explicitly `undefined`. The Chrome Declarative Net Request specification mandates that `value` must be a non-empty string when `operation` is `'set'`. As a result, rule 9001 was never successfully registered, and `updateDynamicRules` threw a runtime rejection on every service worker boot (since `STANDARD` is the default).
- **Remediation Applied:**
  Updated `syncReferrerHeaderRule()`:
  - In `STRICT` mode, the rule modifies `requestHeaders: [{ header: 'referer', operation: 'remove' }]` to strip outgoing referrers on cross-origin requests.
  - In `STANDARD` mode, the rule modifies `responseHeaders: [{ header: 'referrer-policy', operation: 'set', value: 'strict-origin-when-cross-origin' }]` to enforce standard origin-only policy on responses.
  - In `OFF` mode, rule 9001 is removed without adding replacement rules.
- **Verification:**
  - TypeScript type check (`npm run typecheck`) passed.
  - Production build (`npm run build`) succeeded.
  - `python -m pytest tests/privacy/test_phase4b_mitigation.py` passed (7/7).
- **Remaining Risk:** None. The rule syntax conforms to Manifest V3 declarativeNetRequest API specifications.

### Bug SB-FIX-002: Hardcoded Null Autopsy Context in Side Panel Privacy Assistant

- **Severity:** MEDIUM / FEATURE REGRESSION
- **Affected Files:**
  - `extension/src/sidepanel/SidePanel.tsx`
  - `extension/src/sidepanel/Autopsy.tsx`
- **Reproduction Steps:**
  1. Open Side Panel and navigate to "Autopsy".
  2. Run autopsy on active tab; report displays successfully.
  3. Switch to "Assistant" tab and ask: "Is this website risky?" or "What can this site see?".
  4. Assistant always responds: `"No website autopsy report is available yet for this tab. Click 'ANALYZE SITE' to run a structural privacy scan."`
- **Root Cause:**
  In `SidePanel.tsx` line 114, `<Chat overview={overview} autopsy={null} />` was hardcoded to pass `autopsy={null}`. The state generated by `Autopsy.tsx` was stored only in `Autopsy`'s local component state and was lost when switching tabs.
- **Remediation Applied:**
  1. Lifted `autopsyReport` state to parent `SidePanel.tsx`.
  2. Enhanced `Autopsy.tsx` with `initialReport` and `onReportChange` props so the scan result propagates to `SidePanel`.
  3. Cached the latest autopsy report in `chrome.storage.local` under `latest_autopsy_report` so it persists across tab switches.
  4. Passed `autopsyReport` into `<Chat overview={overview} autopsy={autopsyReport} />`.
- **Verification:**
  - `Chat.tsx` now receives real autopsy report metrics (unique third-party domains, tracker counts, canvas detection, exposure score).
  - TypeScript build passed.
- **Remaining Risk:** None. Purely additive state management within the Side Panel.

### Bug SB-FIX-003: Popup Companion Buttons Defaulted to Wrong Side Panel Tab

- **Severity:** LOW / UX INCONSISTENCY
- **Affected Files:**
  - `extension/src/popup/Popup.tsx`
  - `extension/src/sidepanel/SidePanel.tsx`
- **Reproduction Steps:**
  1. Open popup.
  2. Click either "SITE AUTOPSY" or "ASSISTANT".
  3. Side panel opened, but always displayed the "Status" tab rather than the clicked feature.
- **Root Cause:**
  `Popup.tsx` had a generic `handleOpenSidePanel()` without any parameter specifying the target tab. `SidePanel.tsx` always initialized `activeTab` to `'status'`.
- **Remediation Applied:**
  1. Updated `handleOpenSidePanel(targetTab?: 'autopsy' | 'assistant')` in `Popup.tsx` to record the requested tab in `chrome.storage.local` under `active_sidepanel_tab` before invoking `chrome.runtime.sendMessage({ type: 'OPEN_SIDEPANEL' })`.
  2. Updated `SidePanel.tsx` `useEffect` to read `active_sidepanel_tab`, switch to the requested tab, and remove the one-shot key.
- **Verification:**
  - Clicking "SITE AUTOPSY" activates the `autopsy` tab.
  - Clicking "ASSISTANT" activates the `assistant` tab.
  - TypeScript build passed.
- **Remaining Risk:** None. Fallback to `'status'` tab remains if no preference was set.

### Bug SB-FIX-004: Potential False Negative in Proxy Reachability Probe on SOCKS5 Ports

- **Severity:** MEDIUM / RESILIENCE
- **Affected File:** `extension/src/background/browserAdapter.ts`
- **Reproduction Steps:**
  1. In `BrowserAdapter.runRouteVerification()`, Step 2 calls `probeProxyReachability('127.0.0.1', torSocksPort)`.
  2. `probeProxyReachability` issues an HTTP GET via `fetch('http://127.0.0.1:9050', { mode: 'no-cors' })`.
  3. If Tor's SOCKS5 daemon abruptly resets TCP connections on non-SOCKS protocol data (rather than returning an HTTP 501 page), `fetch()` rejects, causing `result.proxyReachable` to evaluate as `false`.
  4. Consequently, Step 4 (`probeBrowserOutboundRoute`) is bypassed and the browser route status is marked as `BROWSER_ROUTE_FAILED`.
- **Root Cause:**
  SOCKS5 is a transport-layer protocol, not an application-layer HTTP protocol. Calling `fetch()` against a SOCKS5 port from a browser extension is unreliable because extensions cannot open raw TCP sockets. The Local Shadow Agent already performs an authoritative RFC 1928 SOCKS5 handshake via raw socket.
- **Remediation Applied:**
  In `BrowserAdapter.runRouteVerification()`:
  ```ts
  result.proxyReachable = agentRouteData?.socks5_reachable !== undefined
    ? Boolean(agentRouteData.socks5_reachable)
    : await this.probeProxyReachability('127.0.0.1', torSocksPort);
  ```
  Prioritizes the agent's verified SOCKS5 handshake result while preserving the fetch fallback when the agent route check is omitted.
- **Verification:**
  - All 16 Phase 3 network tests pass.
  - TypeScript build passed.
- **Remaining Risk:** None. Preserves existing behavior when agent data is unavailable.

### Bug SB-FIX-005: Outbound Browser Route Probe Timeout on Cold Tor Circuits

- **Severity:** MEDIUM / FALSE WARNING
- **Affected File:** `extension/src/background/browserAdapter.ts`
- **Reproduction Steps:**
  1. Boot extension and start bundled Tor daemon.
  2. Call `START_ANONYMOUS_SESSION`.
  3. In Step 8, `probeBrowserOutboundRoute(4000)` executes `fetch('https://check.torproject.org/api/ip')`.
  4. On cold 3-hop Tor circuits, initial TLS handshake and exit node DNS resolution takes ~5-6 seconds.
  5. The 4000ms timeout aborts the request, causing `browserRouteStatus = 'BROWSER_ROUTE_FAILED'` and downgrading the session to `DEGRADED`.
- **Root Cause:**
  A 4000ms timeout is overly aggressive for cold Tor circuit handshakes across multiple hops.
- **Remediation Applied:**
  Updated `probeBrowserOutboundRoute` default timeout to 8000ms (8 seconds) in `browserAdapter.ts`. This allows sufficient time for genuine exit node TLS establishment while still preventing indefinite stalls.
- **Verification:**
  - Live acceptance test `node tests/real_world_acceptance.mjs` confirmed Step 8 successfully reported: `[DONE] Browser: BROWSER_ROUTE_VERIFIED | Agent: TOR_ROUTE_VERIFIED`.
  - Session state reliably reaches `PROTECTED` (confidence: `HIGH`).
- **Remaining Risk:** None. Outbound probe remains bounded and will not block background worker indefinitely.

### Bug SB-FIX-006: Kill Switch Not Triggered When Tor Drops During Degraded Session

- **Severity:** HIGH / SECURITY GAP
- **Affected File:** `extension/src/background/privacyController.ts`
- **Reproduction Steps:**
  1. Start an anonymous session that enters `DEGRADED` state (e.g. proxy is actively configured to 127.0.0.1:9050, but browser verification was incomplete).
  2. Terminate the Tor process (`taskkill /F /IM tor.exe`).
  3. In `privacyController.ts` line 258, the kill switch logic checked: `if (this.state === 'PROTECTED')`.
  4. Because `this.state` was `'DEGRADED'`, the kill switch condition was bypassed, leaving the browser pointing to a dead port instead of actively engaging the port 9 discard blackhole.
- **Root Cause:**
  `privacyController.ts` only evaluated kill switch enforcement when `this.state === 'PROTECTED'`, ignoring active sessions that were in `'DEGRADED'` state.
- **Remediation Applied:**
  Expanded the condition to: `if (this.state === 'PROTECTED' || this.state === 'DEGRADED')`. Any active anonymous session routing traffic through Tor will now immediately engage the fail-closed discard blackhole (port 9) if Tor drops.
- **Verification:**
  - Acceptance test confirmed `killSwitchEngaged: true` and `Active Proxy Port under Kill Switch: 9`.
  - Direct bypass attempt was blocked (`ERR_PROXY_CONNECTION_FAILED`).
  - Upon Tor restart, session successfully auto-recovered to `PROTECTED`.
- **Remaining Risk:** None. Ensures fail-closed security for all active session states.

## 3. Unresolved Technical Limitations & Observations

The following items are NOT defects, but structural browser limitations and planned future architectural items:

1. **L-005 / L-006: Inability to Inspect Kernel-Level DNS Queries in Chromium:**
   - Manifest V3 extensions operate above the OS network stack. While SOCKS5 requests remote hostname resolution, an extension cannot inspect UDP packets on port 53.
   - Status: Kept honestly classified as `PARTIAL` protection.
2. **L-007: Fingerprint Mitigation Requires Normalized Canvas Profile:**
   - Fingerprint protection is currently `DETECTION ONLY`. Introducing random noise creates high-entropy signatures. Real mitigation requires an engine that returns consistent, normalized values across canvases and contexts.
   - Status: Kept honestly classified as `DETECTION ONLY`.
3. **L-009: Storage Isolation via Cleanup Rather Than Kernel Containers:**
   - Chrome MV3 does not expose per-tab storage containers. Data written during the session exists in normal origin storage until purged at session exit.
   - Status: Kept honestly classified as `PARTIALLY_PROTECTED` (`STORAGE_CLEANUP_VERIFIED`).
4. **Pre-Dispatch URL Tracking Parameters on Omnibox Navigation:**
   - `window.history.replaceState` runs at `document_start` on the client page. For cold top-level navigations directly typed into the address bar, the initial HTTP request leaves the browser before the client script executes.
   - Status: Tracked for future declarativeNetRequest redirect rules (`redirect: { transform: { queryTransform: ... } }`) in Phase 5/6.
